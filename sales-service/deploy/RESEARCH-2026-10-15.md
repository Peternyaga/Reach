## Additive migration and rollback

`backend/migrate.php` creates `lead_research` and `research_requests` if absent. Both inherit the parent lead/workspace boundary; no submitted workspace/project can choose access. `activities.body` widens from TEXT to MEDIUMTEXT so old/new research revisions fit without truncation. The migration is repeatable and does not seed customer IDs, rewrite notes or change sales stages. Run it before serving the new frontend.

The existing `install-upgrade.sh` first requires the installed private config/site, backs up the database and application under `fieldwork-backups/<UTC timestamp>`, and only then copies files and runs migrations. It preserves `fieldwork/config.local.php`, mail encryption key and runtime/session data. Failure restores previous application files; schema changes are not automatically reversed. The additive research tables and widened text can remain while restoring older application files. Restore a database backup only through a deliberate maintenance procedure that accounts for all writes since that backup.
